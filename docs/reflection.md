# Personal Reflection

## 1. OOP Concepts Applied

In this project, several advanced object-oriented programming concepts were applied to model the food pantry's resource allocation problem. First, inheritance and sealed traits were utilized to establish a compile-safe hierarchy, where the sealed trait PantryItem serves as the base for all inventory items, subclassed by PerishableFood and ShelfStableFood. The sealed modifier ensures compile-time completeness, preventing arbitrary external subclasses and enabling exhaustive pattern matching inside serialization and matching engine algorithms. Second, subtype polymorphism was leveraged through the PantryItem trait by declaring an abstract method displayDetails, which is explicitly overridden in PerishableFood to display expiration dates, storage, and dietary categories, and in ShelfStableFood to display storage, unit types, and dietary tags. Third, parametric polymorphism was implemented using a generic repository class DataRepository[T] and a generic serializer interface `RecordSerializer[T]` to handle data storage. This design allows the same database reading and writing logic to serve both PantryItem and FamilyRequest records, keeping the codebase clean and adhering to the DRY principle. Fourth, encapsulation was maintained by using private fields, such as private val filePath in the repository, which encapsulate internal file paths and state variables, preventing client classes from tampering with underlying persistence logic. Finally, the design prioritizes immutability by representing all model classes, such as PerishableFood, ShelfStableFood, FamilyRequest, and DistributionPlan, as immutable case classes. State transitions are achieved by returning new copies of items with modified quantities using recursive functions instead of mutable loops or collections.

## 2. Problems Encountered

During implementation, several key design and compilation problems were encountered and successfully resolved. One major issue involved ScalaFX TableView column assignment, where reassigning lists directly to tableView.columns resulted in a reassignment compilation error because columns are defined as read-only values. The solution was to use the ++= operator to add columns in-place, which conforms to the ScalaFX API. Another significant challenge was handling unused warnings with event handlers under the strict -Wunused:all compiler flag. The ScalaFX handle implicit handler wrappers were flagged as warnings in Scala 3 due to old-style implicit parameter definitions inside the external dependency jar. To achieve zero warnings, a dual solution was required: a custom handle method was authored locally in AppContext.scala to shadow the default implicit-based event handler conversion on the closure block, and the "-Wconf:msg=Implicit parameters:s" compiler option was configured in `build.sbt` to silence warnings triggered when assigning events to ScalaFX property setters like onAction.

## 3. Strengths and Weaknesses

The current implementation of the application features distinct architectural strengths and some minor weaknesses. The primary strength of this design is that the repository and logic layers are completely decoupled from the ScalaFX graphical user interface. The waste-minimizing allocation engine operates as a pure mathematical function, making it highly testable and robust. Additionally, robust exception handling via scala.util.Try ensures that invalid file formats or parsing failures do not lead to application crashes. On the other hand, the primary weakness is that although the application leverages reactive properties (ObservableBuffer), updating a record requires reloading the entire dataset from the CSV file. Introducing an in-memory cached state service would improve UI performance and scalability for larger datasets.
